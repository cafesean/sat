**PostgreSQL Database Schema Design Best Practices for SaaS Applications**

**Preamble:**
This document outlines the best practices for designing database schemas in PostgreSQL, particularly for SaaS applications. The goals are to ensure data integrity, scalability, maintainability, performance, and clarity. All new schema designs and modifications should be checked against these guidelines.

**I. Core Principles:**

1.  **Clarity & Readability:** The schema should be easily understandable. Names should be intuitive and self-documenting where possible.
2.  **Consistency:** Adhere strictly to chosen conventions across the entire schema.
3.  **Data Integrity:** Prioritize the correctness and validity of data through constraints and appropriate data types.
4.  **Performance:** Design for efficient querying and data manipulation, but don't prematurely optimize without measurement.
5.  **Scalability:** Design with future growth in mind, especially concerning data volume and concurrent users (tenant isolation is key for SaaS).
6.  **Maintainability:** The schema should be easy to evolve and manage over time.

**II. Naming Conventions:**

1.  **General Case:** Use `lowercase_snake_case` for all identifiers (tables, columns, functions, indexes, constraints, schemas, etc.).
    *   *Rationale:* PostgreSQL folds unquoted identifiers to lowercase. Quoting is cumbersome. Snake case is standard and readable.
2.  **Tables:**
    *   Use **singular nouns** (e.g., `user`, `product_order`, `tenant_setting`).
    *   For join tables (many-to-many), combine the names of the two tables they connect, typically in alphabetical order or `parent_child` order if clear (e.g., `group_user`, `post_tag`).
3.  **Columns:**
    *   **Primary Keys:** Name them `id`.
    *   **Foreign Keys:** Use the format `referencing_table_singular_name_id` (e.g., in `product_order` table, FK to `user` is `user_id`).
    *   **Boolean Flags:** Prefix with `is_`, `has_`, `can_`, `should_` (e.g., `is_active`, `has_trial_ended`).
    *   **Timestamps:** Use suffixes like `_at` or `_on` (e.g., `created_at`, `updated_at`, `published_on`, `expires_at`).
    *   **Descriptive Names:** Prefer clarity over brevity (e.g., `user_language_preference` instead of `lang_pref`).
4.  **Relational Clarity in Naming:**
    *   For entities that are always direct children of another specific entity and make little sense outside that parent's context, consider the `ParentChild` naming convention for the child table (e.g., if a `Question` can *only* belong to a `Passage`, name the table `passage_question`).
5.  **Indexes:**
    *   Prefix: `ix_` for general indexes, `uix_` for unique indexes.
    *   Format: `[prefix]table_name_column_names` (e.g., `ix_users_email`, `uix_users_tenant_id_username`).
6.  **Constraints:**
    *   Prefix and describe:
        *   Primary Key: `pk_table_name` (e.g., `pk_users`).
        *   Foreign Key: `fk_table_name_referencing_table_name_column_name` (e.g., `fk_orders_users_user_id`).
        *   Unique: `uq_table_name_column_names` (e.g., `uq_users_email`).
        *   Check: `chk_table_name_condition_description` (e.g., `chk_products_price_positive`).
    *   *Rationale:* Explicitly named constraints are crucial for debugging and schema management.

**III. Data Types:**

1.  **Timestamps:**
    *   **`TIMESTAMP WITH TIME ZONE` (`timestamptz`)**: Use this for *all* date/time storage that represents a specific point in time. Data is stored in UTC and converted to/from the session's timezone. Default precision is sufficient unless higher is explicitly needed (e.g., `timestamptz(3)` for milliseconds).
2.  **Numbers:**
    *   **`INTEGER` / `BIGINT`**: For whole numbers. Choose `BIGINT` if `INTEGER` limits (approx +/- 2 billion) might be exceeded (common for IDs in high-volume tables).
    *   **`NUMERIC(precision, scale)` / `DECIMAL(precision, scale)`**: For monetary values or any exact fractional values. **Never use `FLOAT` or `REAL` for money.** (e.g., `NUMERIC(12, 2)` for amounts up to 9,999,999,999.99).
3.  **Text:**
    *   **`TEXT`**: Preferred for variable-length strings. Performance is equivalent to `VARCHAR` without `(n)`.
    *   **`VARCHAR(n)`**: Use only if there is a *strict, immutable business rule* for maximum length that must be enforced at the database level.
4.  **Primary Key Data Type:**
    *   **`BIGSERIAL` (auto-incrementing `BIGINT`)**: Good default for most tables.
    *   **Native `UUID`**: Excellent for distributed systems, client-side ID generation, or obscuring counts. If used, ensure the PostgreSQL native `uuid` type is used (e.g., via `uuid_generate_v4()` or `gen_random_uuid()`).
5.  **Booleans:** Use `BOOLEAN` (`TRUE`, `FALSE`, `NULL`).
6.  **JSON:** Use `JSONB` for semi-structured data due to its efficiency and indexing capabilities. Avoid `JSON`.
7.  **Enumerated Types (PostgreSQL `ENUM`):**
    *   Define custom `ENUM` types for columns with a small, fixed set of possible string values (e.g., `CREATE TYPE order_status AS ENUM ('pending', 'processing', 'shipped');`).
    *   *Rationale:* Type safety, smaller storage than text, better performance.

**IV. Primary Keys (PKs):**

1.  **Existence:** Every table must have a PK.
2.  **Name:** `id`.
3.  **Simplicity:** Prefer single-column PKs. Composite PKs should be used sparingly and only if they represent a natural key that is inherently unique and stable.
    *   If including `tenant_id` in PKs (for partitioning strategies or co-location), this is a valid exception.
4.  **Immutability:** PK values should never change once assigned.

**V. Foreign Keys (FKs) & Relationships:**

1.  **Definition:** Always define FK constraints to enforce referential integrity at the database level. Do not rely solely on application logic.
2.  **Matching Types:** FK column type must exactly match the referenced PK column type.
3.  **`ON DELETE` Behavior:**
    *   **`RESTRICT` (or `NO ACTION`):** Default and often safest. Prevents deletion of a parent row if children exist.
    *   **`SET NULL`:** Use if the child row can logically exist without the parent (FK column must be nullable).
    *   **`SET DEFAULT`:** Use if the child row should revert to a default parent (FK column must have a default, and that default must exist in the parent table).
    *   **`CASCADE`:** Use with *extreme caution* and only when the child entity's lifecycle is strictly dependent on the parent and it has no independent meaning. Document every use of `CASCADE`.
4.  **`ON UPDATE` Behavior:** Typically `RESTRICT` or `CASCADE` (if PKs can change, which they shouldn't ideally).
5.  **Indexing FKs:** **Always create indexes on FK columns.** PostgreSQL does not do this automatically. Unindexed FKs are a common cause of poor join performance.

**VI. Constraints (Beyond PK/FK):**

1.  **`NOT NULL`:** Enforce for all columns that cannot logically be empty.
2.  **`UNIQUE`:** Apply to columns or groups of columns that must be unique within their scope (e.g., `email` in a `users` table, potentially `(tenant_id, username)`). Name them explicitly.
3.  **`CHECK`:** Use for domain integrity and business rules that can be validated at the row level (e.g., `price > 0`, `end_date >= start_date`). Name them explicitly.

**VII. Indexing Strategy:**

1.  **Automatic:** PKs are automatically indexed.
2.  **Mandatory:** Index all FK columns.
3.  **Query-Driven:** Index columns frequently used in:
    *   `WHERE` clauses (especially for high-cardinality columns).
    *   `JOIN` conditions (already covered by FK indexing rule).
    *   `ORDER BY` and `GROUP BY` clauses.
4.  **`JSONB` Indexing:** Use GIN indexes for searching within `JSONB` columns (e.g., `CREATE INDEX ix_table_jsonb_col ON table USING GIN (jsonb_col);`).
5.  **Partial Indexes:** Consider for very large tables where queries frequently target a specific subset of rows (e.g., `CREATE INDEX ix_orders_pending_shipment ON orders (order_date) WHERE status = 'pending_shipment';`).
6.  **Avoid Over-Indexing:** Indexes improve read performance but slow down writes (`INSERT`, `UPDATE`, `DELETE`) and consume disk space. Regularly review index usage. Use `EXPLAIN ANALYZE` to verify index effectiveness.

**VIII. SaaS Multi-Tenancy (Column-Based with RLS):**

1.  **`tenant_id` Column:** Add a `tenant_id` column (e.g., `UUID` or `BIGINT` referencing a `tenants` table) to *every table* containing tenant-specific data. This column should be `NOT NULL`.
2.  **FK to `tenants` Table:** The `tenant_id` column should be an FK to a central `tenants` table.
3.  **Composite Indexing/Constraints:** Include `tenant_id` in PKs (e.g., `PRIMARY KEY (tenant_id, id)`) or, more commonly, in unique constraints and indexes to ensure uniqueness *within a tenant* (e.g., `UNIQUE (tenant_id, email)`).
4.  **Row-Level Security (RLS):** Implement RLS policies on all tenant-specific tables to automatically filter data based on the current tenant context (e.g., `current_setting('app.current_tenant_id')`). This is a critical security measure.

**IX. Normalization & Denormalization:**

1.  **Start with 3rd Normal Form (3NF):** Design to reduce data redundancy and improve data integrity.
2.  **Strategic Denormalization:** Only denormalize for specific, measured performance reasons after identifying bottlenecks. Document the rationale and potential data consistency trade-offs. Common examples: adding counters, pre-calculating values.

**X. Auditability & Soft Deletes:**

1.  **Audit Columns:** Include in most tables:
    *   `created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`
    *   `updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()` (use a trigger to auto-update)
    *   `created_by_user_id [type_matching_user_id]` (nullable if system can create)
    *   `updated_by_user_id [type_matching_user_id]` (nullable)
2.  **Soft Deletes (Optional):** If data should be recoverable or historically tracked after "deletion," consider a `deleted_at TIMESTAMPTZ NULL` column. Queries must then explicitly filter `WHERE deleted_at IS NULL`.

**XI. Security (Database Level):**

1.  **Principle of Least Privilege:** Application database users should only have the minimum necessary permissions (`SELECT, INSERT, UPDATE, DELETE` on specific tables/schemas, `EXECUTE` on specific functions). Avoid `SUPERUSER` for application connections.
2.  **RLS:** (See Section VIII for multi-tenancy).

**XII. Maintainability & Evolution:**

1.  **Schema Migrations:** Use a dedicated schema migration tool (e.g., Flyway, Liquibase, Alembic). All schema changes must be scripted and version-controlled. Never apply schema changes manually to production.
2.  **Comments:** Use PostgreSQL `COMMENT ON TABLE ... IS ...;` and `COMMENT ON COLUMN ... IS ...;` to document the purpose of tables and columns.

**AI Check Prompt Template:**

"Review the following proposed database schema changes / new table definitions against the established 'PostgreSQL Database Schema Design Best Practices for SaaS Applications' document. Specifically, verify adherence to:

1.  **Naming Conventions:**
    *   Are all identifiers `lowercase_snake_case`?
    *   Are table names singular nouns?
    *   Do join table names appropriately combine parent entities?
    *   Are column names for PKs (`id`), FKs (`referencing_table_singular_id`), booleans (`is_/has_`), and timestamps (`_at/_on`) correct?
    *   Is relational clarity present in names (e.g., `ParentChild` for mandatory child tables)?
    *   Are indexes and constraints explicitly and conventionally named?

2.  **Data Types:**
    *   Are `TIMESTAMPTZ` used for all point-in-time date/time fields?
    *   Is `NUMERIC`/`DECIMAL` used for monetary values?
    *   Is `TEXT` used for variable strings (unless `VARCHAR(n)` is strictly justified)?
    *   Is the PK type appropriate (`BIGSERIAL` or native `UUID`)?
    *   Is `JSONB` used for JSON data?
    *   Are PostgreSQL `ENUM` types used for fixed sets of string values?

3.  **Primary & Foreign Keys:**
    *   Does every table have a PK named `id`?
    *   Are FKs defined for all relationships?
    *   Is the `ON DELETE` behavior explicitly chosen and justified (especially for `CASCADE`)? Is `RESTRICT` or `SET NULL` the default consideration?
    *   Are all FK columns indexed?

4.  **Constraints:**
    *   Are `NOT NULL`, `UNIQUE`, and `CHECK` constraints appropriately applied and named?

5.  **Indexing:**
    *   Beyond PK/FK indexes, are there appropriate indexes for common query patterns (`WHERE`, `ORDER BY`, GIN for `JSONB`)?
    *   Is there any risk of over-indexing?

6.  **SaaS Multi-Tenancy (if applicable):**
    *   Is there a `tenant_id` on all tenant-specific tables?
    *   Is `tenant_id` part of relevant unique constraints/indexes?
    *   Is RLS planned or in place?

7.  **Normalization & Denormalization:**
    *   Does the design adhere to 3NF unless denormalization is explicitly justified for performance?

8.  **Auditability:**
    *   Are standard audit columns (`created_at`, `updated_at`) present with correct defaults/triggers?

9.  **General Clarity & Maintainability:**
    *   Is the purpose of each table and column clear from its name and context?
    *   Are there any ambiguities or potential points of confusion?

Provide a list of deviations, concerns, and recommendations based on these best practices."
